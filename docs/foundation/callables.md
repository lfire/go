# 第 010 讲 · 函数、多返回值、变参与闭包

> 前面每一讲都在写 `main`，但真正让代码可复用、可组合的是函数。Go 的函数有几个和别的语言不太一样的地方：一次能返回多个值（错误处理的基石）、函数本身可以当值传来传去、内部函数能记住外层的变量，还有一条"下班前一定做"的 `defer`。这一讲把这些拼图补齐，地基阶段就此收口。

## 1. 先建立直觉

把函数想成一台贴了说明书的机器：有输入口（参数）、输出口（返回值）和内部流程（函数体）。Go 的机器比常见语言多几样本事：输出口可以不止一个（多返回值）；整台机器可以当零件交给另一台机器（函数作为值）；机器出厂时还能随身带上车间里的某样东西并一直记住它（闭包）；另外可以登记一张"下班前务必执行"的清单（`defer`）。

<ConceptDiagram type="stack-heap" title="函数调用开栈帧，闭包捕获的变量要活得更久" />

闭包这件事正好用第 009 讲的内存模型解释：外层函数的局部变量本该随栈帧一起回收，可一旦被内部函数引用，编译器就会让它<Term word="逃逸" text="变量需要活过当前函数时，编译器把它分配到堆上，由 GC 负责回收。" />到堆上，于是闭包每次调用都能读改同一份状态。理解了这个，"函数为什么能记住东西"就不是魔法了。

<ConceptDiagram type="defer-stack" title="defer 登记的语句按后进先出，在函数返回前执行" />

### 为什么 Go 让错误当返回值，而不是抛异常

多返回值不是语法糖，它支撑了 Go 整个错误处理的风格。`(int, error)` 把"这次操作可能失败"直接写进函数签名，调用方必须显式接住第二个值（或者用 `_` 主动丢弃），于是没有任何一次失败能被人悄悄忽略。

替代方案是异常机制，代价有两层：控制流可以跳过中间任意一层，读代码时看不出哪里会中断；错误类型不在签名里，编译器也帮不上忙，漏处理很常见。Go 把失败变成一个**普通的值**，于是它能被赋值、传递、比较、包装，`errors.Is`、`errors.As` 这套错误链才有立足点（[第 020 讲](/basics/errors)）。错误固定放在最后一个返回值，则是全生态统一的约定：调用方第一行就能 `if err != nil`，工具与静态检查也能据此识别。机器类比里，这相当于第二个输出口专门报"这次加工成没成"，而不打断流水线。

### 为什么 defer 一定要等到函数返回才执行

资源的"打开"和"关闭"最好写在相邻两行，但中间可能从任意分支 `return`。若靠人在每个返回点都补一次关闭，迟早会漏。defer 把"关闭"登记到当前函数的返回路径上，无论从哪个分支走，运行时都会兜底执行。

代价与作用范围绑在一起：defer 属于**整个函数**，所以大循环里会一直堆积到函数结束才执行，可能拖住文件句柄等资源，得拆成小函数（原文易错点第四条）。这是"便利"换来的边界，不是缺陷；理解它，才知道什么时候该把循环体抽成函数。

### 三个能立刻跑的小实验

第一组把"defer 的参数何时求值"与"defer 的语句何时执行"分开验证：

```go
package main

import "fmt"

func main() {
	x := 1
	defer fmt.Println("defer 里的 x：", x)
	x = 9
	fmt.Println("正常流程的 x：", x)
}
```

<OutputBox title="实验一：参数立即求值，语句延迟执行" output="正常流程的 x： 9\ndefer 里的 x： 1" />

逐项读：defer 那一行的参数在**声明时**就求值成 1，后来把 x 改成 9 并不影响它；语句本身被推迟到函数返回前，所以"正常流程"先打印。这两件事分开，才不会误以为 defer 里的变量会跟着后面的修改一起变。

第二组验证闭包捕获的是变量、不是当时的值：

```go
package main

import "fmt"

func main() {
	n := 1
	f := func() { fmt.Println("闭包读到：", n) }
	n = 9
	f()
}
```

<OutputBox title="实验二：捕获变量本身，而非创建时的副本" output="闭包读到： 9" />

闭包捕获的是 `n` 这个变量，不是它被创建那一刻的 1；所以后来改成 9，调用时读到 9。这正是 [第 015 讲](/basics/range-pitfalls) 循环里取地址、闭包捕获出问题的根，也是本讲开头说"被捕获变量会逃逸到堆"的可观察证据。

第三组把变参的位置约束亲手撞一次：试着把 `...int` 写在参数列表中间，再执行 `go build`。

```bash
go build
```

<OutputBox title="实验三：变参必须是最后一个参数" output="./main.go:5:20: can only use ... with final parameter in list" />

报错说明三个点只能用于参数列表的最后一项：它要收走调用时剩余的全部实参，前面若还有其它参数，编译器无法划分边界。改成 `func f(a int, nums ...int)` 再跑，输出为空即通过。

## 2. 语法与规则

先看 Go 最常见的函数形态：一次返回两个值，结果在前、错误在后。

```go
package main

import (
	"errors"
	"fmt"
)

func divide(a int, b int) (int, error) { // 结果在前，错误在后
	if b == 0 {
		return 0, errors.New("除数不能为零")
	}
	return a / b, nil
}

func main() {
	q, err := divide(42, 2)
	if err != nil {
		fmt.Println("出错了")
		return
	}
	fmt.Println("商：", q)
	q2, _ := divide(10, 3) // 用空标识符忽略不需要的值
	fmt.Println("只取商：", q2)
}
```

<OutputBox title="运行结果" output="商： 21\n只取商： 3" guess="true" />

返回多个值时，调用方必须用同等数量的变量接住；不想要的用 `_` 丢掉。把错误放在最后一个返回值是 Go 全生态的惯例，第 020 讲会系统展开错误处理，这里只需要看懂"函数能一次给出结果和它的状态"这件事。返回值也可以命名，写成 `(q int, err error)`，配合裸 `return` 使用，但工程上要谨慎，后面会讲原因。

第二段看变参与"函数作为值"：

```go
package main

import "fmt"

func sum(nums ...int) int { // 变参：调用时可以给任意多个 int
	total := 0
	for _, n := range nums {
		total += n
	}
	return total
}

func apply(f func(int) int, x int) int { // 函数本身也能当参数
	return f(x)
}

func double(n int) int { return n * 2 }

func main() {
	fmt.Println("求和：", sum(1, 2, 3, 4))
	fmt.Println("把函数传进去：", apply(double, 21))
}
```

<LineByLine code="func sum(nums ...int) int {\n    total := 0\n    for _, n := range nums {\n        total += n\n    }\n    return total\n}" :notes='["三个点表示变参，函数内部把它当成一个序列来用","先准备一个累加用的变量，初始为零","逐个取出序列里的元素并累加","循环结束返回总和"]' />

<OutputBox title="运行结果" output="求和： 10\n把函数传进去： 42" />

变参必须是参数列表的**最后一个**，函数内部可以用 `range` 遍历、用 `len` 数个数；手里已有序列时，用 `sum(序列...)` 把它展开传入。`apply` 的签名里 `func(int) int` 是一种<Term word="函数类型" text="由参数与返回值决定的类型；同签名的函数可以赋给同一个变量或作为参数传递。" />，只要签名一致，任何函数都能传进去——这就是回调与策略模式的底座。

第三段把闭包与 `defer` 放在一起看：

```go
package main

import "fmt"

func counter() func() int { // 返回值本身是一个函数
	n := 0
	return func() int { // 匿名函数捕获了外层的 n
		n++
		return n
	}
}

func main() {
	next := counter()
	fmt.Println(next(), next(), next())
	defer fmt.Println("这句最后才执行")
	fmt.Println("正常流程")
}
```

<OutputBox title="运行结果" output="1 2 3\n正常流程\n这句最后才执行" guess="true" />

`counter` 返回的匿名函数带着外层的 `n` 一起活了下来，所以三次调用依次得到 1、2、3。`defer` 则把一条语句登记起来，等当前函数**即将返回时**才执行，因此"正常流程"先打印、被 defer 的那句最后打印。多个 defer 按后进先出的顺序执行，最常见的用途是配对清理资源，第 021 讲会完整展开。

### 推导：闭包为什么能记住外层变量

原文说"被捕获的变量逃逸到堆"，把这条链补完整，闭包就不再像魔法：

| 步骤 | 发生了什么 |
| --- | --- |
| 外层函数的局部变量 | 本该随栈帧一起回收 |
| 内部函数引用了它 | 编译器发现"这份数据要活过当前函数" |
| 触发逃逸 | 变量被分配到堆，由 GC 管理 |
| 闭包被返回、反复调用 | 只要闭包还活着，那份堆上的状态就不被回收 |
| 每次调用 | 读写的是同一份变量，于是计数、累加这类状态能记住 |

由此还能推出两个边界。第一，被捕获变量的生命周期被拉长了：在闭包里顺手抓一个大对象，整块内存都会跟着闭包一起存活，这是原文工程实践提醒"别抓整个请求上下文"的原因。第二，Go 1.22 之前 `for` 与 `for range` 的循环变量是同一份、逐次复用，循环里创建的闭包取地址会全指向最后一份；1.22 起改为每次迭代独立声明，行为随之改变，这个坑的完整拆解在 [第 015 讲](/basics/range-pitfalls)。

### 推导：defer 的执行顺序与时机

多个 defer 按后进先出执行，是因为它们被登记成一个栈：后登记的先弹出。而执行时机是"return 语句求值之后、函数真正把控制权交还调用方之前"，所以它既不是异步的，也不是在另一个 goroutine 里。下面这段把两点一次验证：

```go
package main

import "fmt"

func main() {
	defer fmt.Println("第一个登记")
	defer fmt.Println("第二个登记")
	fmt.Println("正常流程")
}
```

<OutputBox title="后进先出，且都在同一函数里" output="正常流程\n第二个登记\n第一个登记" />

"正常流程"先打印；返回前两个 defer 按登记的相反顺序执行。若 defer 真在另一个 goroutine 里，输出顺序就不可能这样稳定，也不可能保证在函数返回前全部跑完。

### 零基础最容易带进来的四个误解

| 错误理解 | 为什么站不住 | 正确理解 |
| --- | --- | --- |
| defer 是异步的，会在另一个 goroutine 里执行 | 它在当前 goroutine、当前函数返回前同步执行，顺序确定 | 属于当前函数的返回钩子 |
| 变参可以放在参数列表任意位置 | 三个点要收走剩余全部实参，前面还有参数就无法划界 | 变参必须是最后一个参数 |
| 函数类型只看返回值 | 它由参数与返回值共同决定 | `func(int) int` 与 `func(int) string` 是两种不同类型 |
| 一旦 `return`，defer 就不会执行了 | `return` 正是开始执行已登记 defer 的信号 | 返回路径上一定会跑完所有 defer |

## 4. 工程实践

写 Go 风格函数，有几条几乎不会错的默认。签名要短：参数超过四五个就该想想是不是该用一个结构体收拢（阶段二讲结构体）。可能失败的操作一律返回 `(结果, error)`，且错误永远放最后，调用方第一件事就是判错，别把错误和其它返回值混在一起。返回值要不要命名？短函数用普通 `return` 最清楚，命名返回只在"多个返回点、需要在 defer 里修正返回值"这类确有收益的场景才用。

闭包很方便，但要留意它把外层变量的生命周期拉长了：捕获一个大对象会让整块内存跟着闭包一起存活，别在闭包里顺手抓了整个请求上下文。函数作为值最适合做回调、排序比较、策略切换——签名一致就能替换，比塞一堆布尔开关清爽。

`defer` 的工程价值在"打开与关闭写在一起"：拿到文件、锁、连接后立刻 `defer` 关闭，后续无论从哪个分支返回都不会漏。但要记住它作用范围是**当前函数**，所以循环里处理一批资源时，最好把单次处理拆成小函数，让 defer 在每次调用结束就生效，而不是攒到最外层函数才执行。

<Callout type="tip" title="一条诊断线索" text="如果某个闭包里的值怎么都不对，先回头看它是在循环里创建的吗、捕获的是变量还是当时的副本。配合第 009 讲的栈帧模型想一遍：被捕获的变量不在原栈帧里，而是在堆上被多次调用共享，问题往往就出在这里。" />

## 小结与下一讲

- 多返回值是 Go 的核心惯例，`(结果, error)` 让失败显式可见；命名返回要克制使用。
- 变参、函数作为值、闭包让代码能组合出回调与带状态的行为，背后是第 009 讲的栈帧与逃逸。
- `defer` 在返回前按后进先出执行，配对清理资源时最有用，但要避开循环堆积与参数求值时机。
