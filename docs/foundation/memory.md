# 第 009 讲 · 栈、堆、值语义与指针

> 这一讲是整个地基阶段最关键的一讲。后面的接口、逃逸分析、GC、并发安全，几乎全都建立在"变量住在内存里、函数按值传参、指针是地址"这三句话上。零基础最容易在这里留下一个模糊的洞：知道指针"大概能改到外面的变量"，却说不清为什么。我们把栈、堆、值传递、指针、nil 一次讲透，并且明确一个常被误解的事实——变量住在哪里，是由编译器决定的，不是由你写没写 `new` 决定的。

## 1. 先建立直觉

把内存想成一栋楼：**栈**是每层随用随退的临时工位，函数一调用就开一间（叫<Term word="栈帧" text="一次函数调用在栈上分到的区域，存放参数与局部变量，函数返回即整块回收。" />），里面放参数和局部变量，函数一返回整间就退掉，干净利落、不需要谁去打扫；**堆**是长期仓库，东西放进去后由垃圾回收器定期盘点清理。变量就是格子上的标签，值是格子里的内容。

值传递像"复印一份文件交给对方"：对方在复印件上涂改，你手里的原件一点没变。指针则像"告诉对方原件在哪个格子"：对方顺着地址找过去，改的就是原件。Go 的默认行为永远是前者，想用后者必须显式写出来——这个"显式"是第 001 讲那套设计哲学在内存层面的延续。

<ConceptDiagram type="value-pointer" title="传值复制一份，传指针共享同一份" />

两张图合起来就是本讲的全部：第一张说明变量住在哪里、活多久，第二张说明赋值与传参默认复制、指针才共享。记住"默认各持一份"，后面判断任何一段代码会不会改到外部数据，都有了准绳。

### 为什么"默认复制、共享必须显式"值得当成一条设计原则

如果默认按引用传递，函数里对参数的任何一次改动都可能悄悄改到调用方，读代码时就必须追到别处确认"还有谁持有这份数据"。在大型代码库里，这种隐式耦合是极难排查的 bug 来源。Go 反过来把复制设为默认，换来的是**局部性**：看到 `f(x)` 就知道 x 不会被改，推理范围收敛在当前函数里。

代价也很清楚：每次调用多一次拷贝，确实需要共享时必须显式写 `&` 与 `*`。替代方案有两种，各有代价——像某些语言那样区分值类型与引用类型，就要求时刻记住哪一类是什么；全部按引用，则把共享变成默认、把意外修改变成常态。Go 选的是"统一按值，只留指针这一种显式机制表达共享"，规则数量最少。

这里最关键的一环是**指针本身也是一份值**：`reset(p)` 复制的是"地址"这份值，于是两份地址指向同一份数据。理解了它，就不会误以为 Go 存在"引用传递"，也能接受"一切皆值"与"传指针能改到外面"同时成立。复印件与"告诉对方原件在哪个格子"这个类比，说的正是这两种被复制的东西不同。

### 三个能立刻跑的小实验

第一组把"变量住哪由编译器决定"从结论变成可观测事实：

```bash
go build -gcflags=-m main.go
```

<OutputBox title="实验一：编译器打印逃逸决策（节选一行）" output="./main.go:6:6: moved to heap: n" />

`-gcflags=-m` 让编译器把优化与逃逸决策打印出来。`moved to heap: n` 说明返回局部变量地址时，编译器判断它必须活过当前函数，于是把它放到了堆上。这正是原文说"返回局部变量地址是安全的"背后的机制，而不是栈有什么特殊之处。完整的观测方法在 [第 027 讲](/core/escape-analysis)。

第二组验证 nil 是什么、以及解引用它会怎样：

```go
package main

import "fmt"

func main() {
	var p *int
	fmt.Println("p 是 nil 吗：", p == nil)
	fmt.Println(*p)
}
```

<OutputBox title="实验二：零值是 nil，解引用会 panic" output="p 是 nil 吗： true\npanic: runtime error: invalid memory address or nil pointer dereference" />

第一行证明指针的零值确实是 nil；第二行说明解引用 nil 指针会立刻 panic，既不会返回 0，也不会有 GC 替你兜住。所以从函数拿到指针后在边界处先判空，不是多余动作，而是这条行为决定的。

第三组验证"指针本身也是一份值"：

```go
package main

import "fmt"

func main() {
	x := 42
	p := &x
	q := p
	fmt.Println("两个指针相等吗：", p == q)
	*q = 9
	fmt.Println("通过 q 改之后 x：", x)
}
```

<OutputBox title="实验三：复制地址，指向同一份数据" output="两个指针相等吗： true\n通过 q 改之后 x： 9" />

`q := p` 复制的是地址这份值，所以 `p == q` 为真、两者指向同一份数据；通过 `q` 改，原件 `x` 也变成 9。这一条把"复制的是地址、不是数据"验证清楚，也解释了为什么共享不违背"一切皆值"。

## 2. 语法与规则

先看默认行为。函数参数拿到的是副本：

```go
package main

import "fmt"

func zero(n int) { // n 只是调用方那份数据的副本
	n = 0
}

func main() {
	x := 42
	zero(x)
	fmt.Println("传值之后：", x) // 仍是 42
}
```

<OutputBox title="运行结果" output="传值之后： 42" guess="true" />

`zero` 里的 `n` 是 `x` 的副本，把副本改成 0 与 `x` 无关。Go 里一切传参都是值传递，没有例外；所谓"引用传递"在 Go 里并不存在，只是有时复制的那个值本身是个地址。

要改到原件，就传地址。`&` 取地址，`*` 解引用，类型写作 `*int`：

```go
package main

import "fmt"

func reset(p *int) { // 收到的是一个地址
	*p = 0 // 顺着地址改到原变量
}

func main() {
	x := 42
	p := &x // 取 x 的地址
	fmt.Println("地址指向的值：", *p)
	reset(p)
	fmt.Println("改完之后：", x)
	fmt.Println("p 非空吗：", p != nil)
}
```

<LineByLine code="x := 42\np := &x\nreset(p)\nfmt.Println(x)" :notes='["在 main 的栈帧里放一个变量 x，装着 42","取 x 的地址存进 p，p 自己也是一份值，内容是那个地址","把这份地址复制给 reset，函数顺着它找到并改掉 x","因此打印出来是 0，改动确实落到了原件上"]' />

<OutputBox title="运行结果" output="地址指向的值： 42\n改完之后： 0\np 非空吗： true" guess="true" />

注意 `p` 本身也是一个值——它里面装的是地址。所以 `reset(p)` 复制的是"地址这份值"，两个地址指向同一份数据。这解释了为什么传指针能改到外面，却不违背"一切皆值"：复制的东西不同而已。

第三段看两个常被问到的问题：局部变量能不能返回地址，以及 nil 是什么。

```go
package main

import "fmt"

func counter() *int { // 返回局部变量的地址，在 Go 里是安全的
	n := 0
	n++
	return &n // 编译器会让 n 逃逸到堆，返回后依然有效
}

func main() {
	p := counter()
	fmt.Println("计数：", *p)
	*p = 9
	fmt.Println("改后：", *p)
	var q *int = nil // 指针的零值是 nil
	fmt.Println("q 是 nil 吗：", q == nil)
}
```

<OutputBox title="运行结果" output="计数： 1\n改后： 9\nq 是 nil 吗： true" />

`counter` 里的 `n` 看似是栈上的局部变量，把它的地址返回却完全合法：编译器通过<Term word="逃逸分析" text="编译器判断一个变量是否需要活过当前函数，若需要就把它分配到堆上；第 027 讲会用 -gcflags -m 亲眼看它。" />发现它会被外部引用，于是自动把它放到堆上。这和 C 里返回局部变量地址是未定义行为截然不同，是从别的语言转过来时最该纠正的一条直觉。

### 推导：为什么返回局部变量的地址在 Go 里是安全的

原文给了"由逃逸分析兜底"这个结论，把它拆成一条因果链才真的能用来判断其它场景：

| 步骤 | 发生了什么 |
| --- | --- |
| 假设 n 留在栈上 | 函数返回时栈帧整块回收，地址随即失效，这正是 C 里返回局部变量地址是未定义行为的原因 |
| 编译器在编译期发现 | 这个地址会被返回、需要在函数结束后继续被访问 |
| 触发逃逸 | 把 n 分配到堆，而不是栈帧里 |
| 堆由 GC 管理 | 只要还有指针引用着它，就不会被回收 |
| 最终结果 | 返回后 `*p` 依然有效，读写都正常 |

所以安全性不是"Go 的栈比较特别"，而是编译器替你做了分配位置的选择。代价也要记住：这次分配落到了堆上，有分配与 GC 成本。同理，被闭包捕获的变量也是因为"要活过当前函数"才逃逸（[第 010 讲](/foundation/callables)）。判断一个变量在哪，看的是"它会不会被外部继续引用"，不是看写了 `var` 还是 `new`。

### 零基础最容易带进来的四个误解

| 错误理解 | 为什么站不住 | 正确理解 |
| --- | --- | --- |
| 取地址 `&` 与解引用 `*` 是一回事，可以互换 | 两者方向相反：`&` 从值得到地址，`*` 从地址取值（或声明指针类型） | 记成"一个往地址走、一个往数据走" |
| nil 与 0、空串差不多，可以混着比较 | nil 只对指针、切片、map、接口等类型有意义，没有独立类型 | `nil == 0` 连类型都对不上，会编译失败 |
| 指针变量里存的就是那份数据 | 它存的是地址，数据还在原来的格子里 | `p == q` 比的是地址是否相同，不是数据 |
| 函数一返回，里面所有局部变量都立刻消失 | 被闭包捕获、或地址被返回的变量会逃逸到堆继续存活 | 栈帧回收只针对留在栈上的部分 |

其中第二条可以直接撞一次编译器：写 `var r *int` 之后加一行 `fmt.Println(r == 0)`，再执行 `go build`。

```bash
go build
```

<OutputBox title="nil 不是 0：类型层就被拦下" output="./main.go:7:15: invalid operation: r == 0 (mismatched types *int and untyped int)" />

逐项读：`./main.go:7:15` 是位置，`mismatched types` 说明指针类型和整数根本不在同一个比较体系里。正确的判空写法是 `r == nil`。这也提醒：nil 是一个"只属于某几类类型的零值"，不是能到处用的通用空值。

## 4. 工程实践

工程上的默认答案很明确：**优先值语义**。按值传递的代码更容易推理——看到参数就知道外面那份不会被改；小对象按值复制反而更利于逃逸分析留在栈上，对缓存也更友好，还能减少堆分配与 GC 压力。别因为"听说指针更快"就把所有参数都改成指针，那往往既没快多少，又引入了 nil 风险和隐式共享。

指针只在三种情况下值得用：确实要修改调用方持有的那份数据；对象很大、复制成本明显（第 026 讲会量化）；需要表达"这个字段可能没有"，用 nil 表示缺省。此外还有一处一致性考虑：同一个类型的方法接收者要么全用值、要么全用指针，别混着来，第 018 讲会讲方法集与这条规则的关系。

<Callout type="tip" title="共享是要还的" text="指针把共享变成显式，也把「谁能改这份数据」变成了需要追踪的问题：多个地方持有同一地址时，改动会互相看见，到了并发场景就是数据竞争（阶段四）。所以指针要用在刀刃上，并尽量缩小它的可见范围；边界函数拿到指针先判 nil，再谈使用。" />

`nil` 检查放在系统边界最划算：解析外部输入、查缓存未命中、可选配置项这些地方返回 nil 很自然；而在内部已确保非空的路径上层层判空，只会把代码淹掉。判断标准始终是"这份数据有没有可能不存在"，而不是"是不是指针"。

## 小结与下一讲

- 栈帧随函数返回自动回收，堆交给 GC；变量住哪由编译器逃逸分析决定。
- 值传递复制副本、指针传地址；`&` 与 `*` 配合，指针本身也是值。
- 优先值语义，指针只用于需要修改、避免大对象拷贝或表达可选的场景；nil 要在边界判空。
