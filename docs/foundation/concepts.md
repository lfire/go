# 第 005 讲 · 程序、数据、值与类型

> 零基础学编程，最容易缺的从来不是某条语法，而是"程序到底在干什么"这幅心智图。没有它，变量、类型、函数都像一堆要死记的规则。这一讲先补这幅图：程序就是数据加处理数据的步骤，变量是装值的盒子，类型是盒子上写死的"只能放什么"。把这三件事想通，后面每一讲的新语法都能挂到同一个架子上。

## 1. 先建立直觉

把程序想成一间厨房：数据是食材（数字、文字、真假），处理是菜谱上的步骤（相加、比较、拼接、判断），变量是贴了标签的保鲜盒，类型就是盒子上写的一行字——"这个盒子只放整数"或"只放文字"。厨师不需要记住每份食材长什么样，只要照着标签取用即可；而如果有人想把一段文字倒进"只放整数"的盒子，主管会在开工前就拦下来，这位主管就是编译器。

这里有个最容易混的区分：**值**是"42 这个数本身"，它是抽象的、不会变的；**变量**是"贴着 age 标签、当前装着 42 的那个盒子"。盒子里的东西可以换，但 42 永远是 42。把一个盒子的内容倒进另一个盒子，倒过去的是一份副本，两个盒子从此互不相干。

<ConceptDiagram type="value-pointer" title="值、变量与复制：b := a 到底发生了什么" />

图上左侧就是本讲的核心：默认赋值复制出一份新数据，改动其中一个不影响另一个。右侧的指针是第 009 讲才展开的内容，先记住 Go 的默认是左边这种"各持一份"，需要共享时才显式用指针。

### 为什么"程序 = 数据 + 处理"值得单独摆出来

零基础最容易把编程理解成"背一堆语法规则"。其实任何程序都能归约到一句话：把输入数据按若干步骤变成输出数据。往机器层面追一层，CPU 只做两件事——从内存取数、按指令做运算再存回去；编程语言只是把这两件事包装成人能读的形式。于是三个抽象刚好一一对应：**变量**对应数据，**运算符与函数**对应处理，**类型**对应"这批数据允许被怎样处理"的约定。

有了这个架子，后面每一讲的新语法都能挂上去：控制流决定"处理"走哪条分支（[第 014 讲](/basics/control-flow)），函数把一段"处理"打包复用（[第 010 讲](/foundation/callables)），结构体把多份"数据"打包成一个值（[第 017 讲](/basics/structs)），接口把"能对这批数据做哪些处理"抽象出来（[第 019 讲](/basics/interfaces)）。学语法时先问"它是在组织数据，还是在组织处理"，就不必死记。

厨房类比还能再推一层：顾客不关心是哪位厨师做的，只关心"食材进去、菜出来"。把数据与处理分开，才能换厨师（换实现）而不改菜单（调用方），这正是后面接口与解耦的根。

### 三个能立刻跑的小实验

第一组实验回答"类型到底是谁定的"。下面这段一行类型标注都没写，编译器仍会给每个字面量和表达式一个确定的类型：

```go
package main

import "fmt"

func main() {
	fmt.Printf("字面量 42 的类型：%T\n", 42)
	fmt.Printf("表达式 40 + 2 的类型：%T\n", 40+2)
	fmt.Printf("字面量 3.14 的类型：%T\n", 3.14)
	fmt.Printf("字面量 true 的类型：%T\n", true)
}
```

<OutputBox title="实验一：没写类型，类型却早已定好" output="字面量 42 的类型：int\n表达式 40 + 2 的类型：int\n字面量 3.14 的类型：float64\n字面量 true 的类型：bool" />

逐项读：整数字面量默认 `int`，浮点字面量默认 `float64`，`true` 默认 `bool`，而表达式的类型由参与运算的值决定。没有任何一步是"运行时才猜类型"——这正是静态类型最底层的含义：类型由编译器按规则赋予并固定。默认类型的规则会在 [第 007 讲](/foundation/numeric) 展开。

```bash
go doc fmt.Printf
```

<OutputBox title="实验二：类型也写在函数签名里（节选一行）" output="func Printf(format string, a ...any) (n int, err error)" />

`format string` 把第一个参数钉死为字符串，`(n int, err error)` 把两个返回值的类型写明白。编译器正是拿这份签名去核对每次调用；`go doc` 能把它随手查出来，说明类型信息在编译期就完整存在，而不是运行时才有。

第三组实验把"数据 + 处理"这句口号变成可观察的事实：同一份数据，换不同的处理步骤，结果就不同。

```go
package main

import "fmt"

func main() {
	// 同一份数据，一次声明、反复使用
	a, b := 12, 3
	// 处理一：相加
	fmt.Println("相加：", a+b)
	// 处理二：相乘
	fmt.Println("相乘：", a*b)
	// 处理三：取较大者
	fmt.Println("较大者：", max(a, b))
}
```

<OutputBox title="实验三：数据没变，结果随处理而变" output="相加： 15\n相乘： 36\n较大者： 12" />

`a`、`b` 从头到尾没被改动，三次输出全由不同的"处理"决定。`max` 是 Go 1.21 起内置的函数，用它只是为了说明"处理"也可以是一个现成的函数，而不只是运算符。

## 2. 语法与规则

先看一段最小程序，把"数据 + 处理"落到实处：

```go
package main

import "fmt"

func main() {
	price := 12            // 数据：单价这个整数
	count := 3             // 数据：数量这个整数
	total := price * count // 处理：把两份数据相乘，得到新数据
	fmt.Println("合计：", total) // 处理：把结果送到屏幕
}
```

<OutputBox title="运行结果" output="合计： 36" />

`price`、`count`、`total` 都是变量，`12`、`3`、`36` 是值，`*` 是处理。整段程序没有别的秘密：把数据装进盒子，按步骤算出新数据，再输出。哪怕是最复杂的服务，拆到底也是这三件事的组合。

第二段代码验证"赋值是复制"：

```go
package main

import "fmt"

func main() {
	a := 42       // a 这个盒子当前装着值 42
	b := a        // 把 42 复制一份，装进新盒子 b
	b = 9         // 只换掉 b 盒子里的东西
	fmt.Println(a, b) // a 仍是 42，b 变成 9
}
```

<LineByLine code="a := 42\nb := a\nb = 9\nfmt.Println(a, b)" :notes='["声明变量 a，把整数值 42 放进去，类型推断为 int","声明 b 并复制 a 当前的值，此刻两个盒子各有一份 42","只给 b 重新赋值为 9，a 完全没有被碰过","因此打印结果是 42 和 9，两个变量彼此独立"]' />

<OutputBox title="运行结果" output="42 9" guess="true" />

这个"默认复制"是 Go 最重要的默认值之一。它让函数里改一个参数不会意外改到调用方的变量，也让代码更容易推理——你看到 `b := a` 就知道从此是两份数据，不用追到别处去猜谁还持有它。

第三段代码看类型。每个值在编译期都有一个确定的类型：

```go
package main

import "fmt"

func main() {
	var count int = 3 // 显式写出类型：count 只能是 int
	name := "Go"      // 不写类型，编译器由右值推断出 string
	ok := true        // 推断出 bool
	fmt.Printf("%T %T %T\n", count, name, ok)
}
```

<OutputBox title="运行结果" output="int string bool" guess="true" />

`%T` 会打印值的类型。注意 `name := "Go"` 并没有写类型，但推断不等于随意：编译器在那一刻就把它定成 `string`，之后再给它赋整数会直接编译失败。<Term word="类型推断" text="由右值自动确定变量类型，但类型一旦确定就在编译期固定，不是运行时才决定。" />

| 概念 | 是什么 | 会不会变 | 类比 |
| --- | --- | --- | --- |
| 值 | 数据本身，如 42、字符串 Go | 不会变 | 食材 |
| 变量 | 有名字、装着某个值的容器 | 内容可换 | 贴标签的保鲜盒 |
| 类型 | 这个容器允许装哪一类值 | 声明时定死 | 盒子上的标签 |
| 处理 | 对值做运算或判断的步骤 | 按代码执行 | 菜谱步骤 |

## 3. 深入一步

<Term word="静态类型" text="变量的类型在编译期确定且不可更改，编译器据此核对每一步操作是否合法。" />

类型系统不是给编译器找麻烦，它至少带来三样实在的好处。第一，**把错误提前**：把字符串传给只接受整数的位置，编译期就拦下，不必等线上跑错路径才发现。第二，**让代码自带文档**：看到 `count int` 就知道这里该是数量，比读注释可靠，因为注释会过期而类型不会。第三，**让编译器能确定内存与操作**：知道一个值是 `int` 还是 `string`，才能决定给它几个字节、用哪条机器指令。IDE 的补全与跳转同样依赖这份确定的类型信息。

### 推导：类型系统的三项价值分别从哪来

原文列了"提前报错、自带文档、确定内存与指令"三个好处，把它们各自依赖的前提拆开，才知道这些好处不是白来的：

| 价值 | 依赖的前提 | 如果换成动态类型会失去什么 |
| --- | --- | --- |
| 提前报错 | 编译器握有每个名字的固定类型标签，每次操作都核对 | 类型错误要等执行到那条路径才暴露，常藏在冷分支里 |
| 自带文档 | 类型被编译器强制检查，改名或改实现时不会悄悄过期 | 只能靠注释说明，而注释没有强制力、会随代码演化失真 |
| 确定内存与指令 | 知道是 `int` 还是 `string`，才能决定占几个字节、用哪条机器指令 | 运行时才判定类型，就得带上额外描述信息并做动态派发 |

三项其实是同一件事的三个侧面：**编译期就确定的类型信息**。它同时被编译器（查错、生成代码）、IDE（补全、跳转）和人（读代码）复用，这也是 [第 001 讲](/guide/opening) 说"静态类型是编译型的搭档"的原因。

### 零基础最容易带进来的四个误解

| 错误理解 | 为什么站不住 | 正确理解 |
| --- | --- | --- |
| 类型推断等于动态类型 | 推断只在声明那一刻发生一次，之后类型同样固定 | 推断是"帮你省掉写类型"，不是"允许以后换类型" |
| 值会跟着变量一起变 | 42 这个数本身恒定，变的是盒子里装的东西 | 变量是容器、值是内容，赋值换的是内容 |
| 静态类型只是啰嗦版的注释 | 注释不参与编译、会过期；类型被编译器强制核对 | 类型是能被机器检查的约束，注释不能 |
| 声明后没赋值的变量里是随机垃圾值 | 这是从 C 带过来的直觉；Go 每种类型都有确定零值 | 声明即可用，不会出现未初始化崩溃 |

最后一条配一段可编译代码，把"零值"与"随机值"彻底分开：

```go
package main

import "fmt"

func main() {
	var count int   // 零值 0，不是随机值
	var name string // 零值是空串，不是 nil
	fmt.Println("count：", count, "名字长度：", len(name))
}
```

<OutputBox title="声明即可用的直接证据" output="count： 0 名字长度： 0" />

`len(name)` 能直接调用而不 panic，说明 string 的零值确确实实是空串。完整的零值表在 [第 006 讲](/foundation/variables)，这里只用来证伪"未初始化是随机值"这个迁移过来的直觉。

## 4. 工程实践

真实代码里，类型用得好不好，直接决定后期好不好维护。第一条经验是**让名字和类型一起表达含义**：`count int` 比 `n` 清楚，`elapsed time.Duration` 比 `elapsed int64` 更不容易把毫秒和纳秒搞混。第二条是**用专门的类型表达约束**：订单状态与其散落在一堆裸字符串里，不如定义一个专门的类型，让非法状态在编译期就无处藏身，这条路会在阶段二讲接口与自定义类型时铺开。第三条是**别用万能类型逃避思考**：看到什么都塞进空接口，等于把类型系统给的检查全部退掉，编译器能帮的忙就一点不剩了。

还有个很实用的 Go 特色：每个类型都有一个<Term word="零值" text="变量声明后未显式赋值时的默认值，如 int 为 0、string 为空串、bool 为 false。" />。声明了就能用，不会出现"未初始化"的运行时崩溃，这是值语义带来的安静好处，第 006 讲会系统列出。

## 小结与下一讲

- 程序就是数据加处理，变量是装值的盒子，类型规定盒子能装什么。
- Go 默认按值赋值，改动一个变量不会牵动另一个；静态类型在编译期把类型钉死。
- 类型系统的价值是提前报错、自文档化与确定内存布局，工程上应让类型替你表达约束。
