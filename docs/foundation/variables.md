# 第 006 讲 · 变量、常量、iota 与作用域

> 第 005 讲建立了"值、变量、类型"的模型，这一讲把"怎么写出来"补齐。声明有几种写法、没赋值时变量里是什么、不变的量怎么表达、一组枚举怎么自动编号、名字在多大范围内可见——这些是写每一行代码都要用到的基础。它们看起来琐碎，却恰恰是零基础最容易 silently 出错的地方：一个不小心，改到的就不是你以为的那个变量。

## 1. 先建立直觉

继续用厨房类比：声明变量就是领一个贴好标签的盒子；零值是盒子出厂时自带的默认内容，所以 Go 里领了盒子就能用，不存在"忘了初始化"的空洞；常量是封死不许再改的盒子；`iota` 是给一整排盒子自动贴流水号的机器，你只写第一张，后面依次加一；作用域则是"这个盒子在哪个区域能被看见"——出了那扇门，名字就不认识了。

<ConceptDiagram type="stack-heap" title="作用域决定变量在哪可见、活多久" />

图上把"随函数调用分配、随栈帧结束回收的局部变量"和"生命周期更长、由垃圾回收管理的对象"分开摆。先借它建立一个印象：声明位置不同，变量的可见范围与存活时间就不同。至于具体谁在栈、谁在堆，由编译器的逃逸分析决定，那是第 009 讲的内容；本讲只关注"名字在哪能被看见"。

### 为什么 Go 要同时留 var 和 := 两种声明

两种写法不是历史包袱，而是各自覆盖了一个对方无法替代的场景。

`:=` 解决的是"函数内高频局部变量"的冗余：右值的类型几乎总能推断出来，再写一遍 `int`、`string` 纯属噪音。它要求左侧至少有一个新变量，是为了让"声明一个新变量"与"给已有变量赋值"在语法上可区分——否则手滑把 `=` 写成 `:=` 就会悄悄造出一个新变量，而这正是本讲后面遮蔽 bug 的主要入口。

`var` 保留在另外两类场合：包级声明（语言规定包级必须用 `var` 或 `const`），以及"先要一个零值容器、稍后再填"的情况，例如 `var count int` 之后才在循环里累加，`:=` 做不到只声明不赋值。

替代方案的代价也清楚：只留 `var` 一种写法，函数内就得处处写类型；只留 `:=`，就没法表达零值声明，也没法在包级定义变量。厨房类比里这是两个动作——"领一个空盒子"（`var`）与"领盒子的同时顺手放进食材"（`:=`）。

### 为什么零值是语言设计，而不是运行时兜底

原文列了零值表，值得补上它为什么存在。如果变量声明后内容是未定义的，那么每个声明都必须紧跟初始化，且"读到一个没初始化的值"会成为一类极隐蔽的运行时 bug——这正是从 C 转过来的人最熟悉的痛。Go 让**每个类型**都有一个确定的零值，于是"声明即可用"成为语言保证：`var count int` 拿到的就是 0，可以直接累加，不必先赋初值。

代价同样要看见：零值可能被误当成"用户确实填了 0"。所以工程上表达"这个字段可能没提供"时，往往要额外用指针的 nil（[第 009 讲](/foundation/memory)）、`comma-ok`（[第 016 讲](/basics/maps)）或哨兵错误（[第 020 讲](/basics/errors)），而不能只靠零值本身。零值解决的是"安全性"，不解决"语义上的缺省"。

### 两个能立刻跑的小实验

下面这段把零值表里的关键区分一次跑出来：字符串的零值是空串而不是 nil，指针的零值才是 nil。

```go
package main

import "fmt"

func main() {
	var (
		i int
		f float64
		s string
		b bool
		p *int
	)
	fmt.Println("数值零值：", i, f)
	fmt.Println("字符串是空串吗：", s == "", "布尔零值：", b)
	fmt.Println("指针是 nil 吗：", p == nil)
}
```

<OutputBox title="实验一：五种类型的零值一次看清" output="数值零值： 0 0\n字符串是空串吗： true 布尔零值： false\n指针是 nil 吗： true" />

逐项读：数值一律归 0；字符串零值是空串，所以可以直接 `len(s)` 或拼接，不会 panic；布尔是 false；只有指针、切片、map、接口这类类型的零值才是 nil。最后这条差别是 [第 009 讲](/foundation/memory) 判空的前提——对一个空串判 `== nil` 是编译错误，因为 string 根本没有 nil 这个零值。

在一个函数里连写两行 `x := 1` 与 `x := 2`，再执行 `go build`：

```bash
go build
```

<OutputBox title="实验二：短声明要求至少一个新变量" output="./main.go:6:4: no new variables on left side of :=" />

报错分三段读：`./main.go:6:4` 是位置，`no new variables` 说明左侧已全部声明过，`on left side of :=` 指出问题出在短声明上。把它改成 `x = 2` 即可通过。亲手撞一次这条错误，比记住"`:=` 左边要有新变量"更牢，也能理解它为什么能拦住一部分意外遮蔽。

## 2. 语法与规则

声明有两种主力写法。完整写法用 `var`，可以只声明不赋值，此时变量自动拿到<Term word="零值" text="变量只声明未赋值时的默认值：数值为 0、字符串为空串、布尔为 false、引用类为 nil。" />：

```go
package main

import "fmt"

func main() {
	var count int          // 只声明，拿到零值 0
	var name string        // 零值是空字符串
	price := 12            // 短声明加推断，等价于 var price int = 12
	fmt.Println(count, name == "", price)
	fmt.Printf("%T %T %T\n", count, name, price)
}
```

<OutputBox title="运行结果" output="0 true 12\nint string int" />

短声明 `:=` 只能在函数内部用，左边至少要有一个**新**变量，否则应该用赋值 `=`。包级变量必须老老实实写 `var`。

| 对比项 | var 完整声明 | := 短声明 |
| --- | --- | --- |
| 可用位置 | 包级、函数内都可以 | 只能在函数内 |
| 是否写类型 | 可写也可省略 | 不写，由右值推断 |
| 能否只声明 | 能，得到零值 | 不能，必须带初值 |
| 左侧全已声明 | 不适用 | 编译报错，应改用赋值 |
| 典型用法 | 包级变量、需要先零值 | 函数内绝大多数局部变量 |

常量用 `const`，一旦声明不能被重新赋值。`iota` 只在 `const` 组里生效，从 0 开始每换一行自动加一；省略表达式的行会沿用上一行的写法，非常适合给一组相关的量自动编号：

```go
package main

import "fmt"

// iota 从 0 起每行加 1；省略表达式的行会重复上一行的写法
const (
	Monday = iota + 1 // 1
	Tuesday           // 2
	Wednesday         // 3
	_ = iota + 1      // 用空标识符跳过编号 4
	Friday            // 5
)

// 表达式也能复用：这里的 1 << (10 * iota) 会被下面两行沿用
const (
	KB = 1 << (10 * iota) // 1
	MB                    // 1024
	GB                    // 1048576
)

func main() {
	fmt.Println(Monday, Tuesday, Wednesday, Friday)
	fmt.Println(KB, MB, GB)
}
```

<OutputBox title="运行结果" output="1 2 3 5\n1 1024 1048576" guess="true" />

第二组常量是工程里很常见的写法：单位换算的倍率用 `iota` 加移位一次生成，比手写三个魔法数字更不容易错，第 012 讲的单位换算器会用到同样的思路。

第三段代码是本讲最该亲手跑一遍的：作用域与遮蔽。

```go
package main

import "fmt"

var total = 100 // 包级变量，首字母小写，只在本包可见

func main() {
	fmt.Println("外层：", total)
	{
		total := 5 // 块内短声明，遮蔽了外层的同名变量
		fmt.Println("块内：", total)
	}
	fmt.Println("回到外层：", total)
}
```

<LineByLine code="var total = 100\nfunc main() {\n    total := 5\n    fmt.Println(total)\n}" :notes='["包级变量在整个包内可见，首字母小写表示不对外导出","进入 main 函数，开始一个新的作用域","块内又声明了同名变量，它是全新的一个，不是给外层赋值","这里打印的是内层那一份，外层那个 total 全程没被碰过"]' />

<OutputBox title="运行结果" output="外层： 100\n块内： 5\n回到外层： 100" guess="true" />

花括号会开出一个新的<Term word="作用域" text="名字生效的代码范围；内层作用域可以声明同名变量遮蔽外层的那一个。" />。内层用 `:=` 声明了同名的 `total`，于是它**遮蔽**（shadow）了外层的变量：块内改的是新盒子，出了块，外层的 100 原封不动。这不是 bug，但极容易在 `if`、`for` 里被忽略，排查时看着"明明赋值了却没生效"。

| int / float64 | 0 | 数值一律归零 |
| string | 空字符串 | 不是 nil，可直接拼接 |

### 推导：为什么内层 := 是遮蔽，而不是改外层

"明明赋值了却没生效"看着像 bug，顺着名字查找规则推一遍就清楚了：

| 步骤 | 发生了什么 |
| --- | --- |
| 编译器遇到一个名字 | 从最内层作用域向外逐层找，最先命中的那个生效 |
| 遇到 `:=` | 它的语义始终是"在当前作用域声明新变量" |
| 当前块里没有同名变量 | 于是新建一个，外层的同名变量从此被挡在后面 |
| 出了这个块 | 内层变量随块结束消失，外层那份从头到尾没被碰过 |

所以遮蔽不是编译器的疏漏，而是"`:=` 把声明与赋值合并成一步"的必然副作用。这也解释了为什么 `if`、`for` 里最容易出事：它们自带一层块作用域，在里面写 `x := 1` 天然就是新变量。排查时沿着花括号往外看一层，比盯着那一行赋值有用得多。原文第三段代码的输出"外层 100、块内 5、回到外层 100"，正是上表这条链跑出来的结果。

### 零基础最容易带进来的四个误解

| 错误理解 | 为什么站不住 | 正确理解 |
| --- | --- | --- |
| `iota` 是一个全局计数器，哪儿都能用 | 它只在 `const` 组里有意义，按行递增，且每个常量组都从 0 重新起算 | 用它的一组常量彼此相关时才用，别把不相干的量凑一组 |
| 常量可以用 `:=` 声明 | `:=` 是变量短声明；常量必须 `const` | 包级不变的量写 `const`，函数内普通变量才用 `:=` |
| 首字母大写表示"这是常量" | 大小写只决定能否被其他包访问，与能不能被重新赋值是两件事 | 小写变量照样能改，大写常量照样不可改 |
| nil 和空串、0 是同一种零值 | nil 只属于指针、切片、map、接口等类型 | string 的零值是空串、数值是 0，它们都不是 nil |

第三条配一段可编译代码直接证伪：

```go
package main

import "fmt"

const Exported = 1 // 大写：可被其他包访问，但仍是常量
var mutable = 2    // 小写：只在本包可见，却可以被重新赋值

func main() {
	mutable = 3
	fmt.Println(Exported, mutable)
}
```

<OutputBox title="可见性与可变性是两回事" output="1 3" />

`Exported` 首字母大写只解决了"别人能不能用"，并没把它变成可改的量；`mutable` 小写却照样被改成了 3。把这两件事分开，[第 011 讲](/foundation/packages) 的导出规则就不会和 `const` 混在一起了。

### 版本与平台边界

| 边界 | 说明 | 归属 |
| --- | --- | --- |
| 长期稳定 | `var`、`:=`、零值、作用域规则从 Go 1.0 起基本没有变化，可以放心依赖 | 与泛型等较新特性不同 |
| Go 1.22 | `for` 与 `for range` 的循环变量改为每次迭代独立声明，影响循环内 `:=` 与闭包的组合 | [第 015 讲](/basics/range-pitfalls) |
| GOARCH | 零值的**值**与平台无关；但 `int`、`uint`、`uintptr` 的**宽度**随 32 位或 64 位变化 | [第 007 讲](/foundation/numeric) |
| 工具能力 | `go vet` 默认不开启 shadow 检查，需要额外分析器，别指望它兜住所有遮蔽 | 原文排查技巧的补充 |
| 初始化顺序 | 包级变量与 `init` 的执行顺序有专门规则，本讲只讲"名字在哪可见" | [第 035 讲](/core/startup) |
| 操作系统 | 声明与作用域规则在 Windows、macOS、Linux 上完全一致 | 平台差异体现在文件系统与路径，不在这里 |

## 4. 工程实践

几条能立刻用上的经验。第一，函数内局部变量优先用 `:=`，简洁且把类型交给编译器；但一旦涉及 `if err != nil` 这类分支，留意别意外遮蔽外层的 `err`。第二，任何"不该被改"的量都用 `const` 表达，让约束由编译器守着，而不是靠注释提醒。`iota` 只用于**一组彼此相关**的枚举或倍率，硬把不相干的常量凑进一个组，反而让后来者看不懂编号含义。第三，包级变量要非常克制：它是全局状态，会让单元测试互相污染，也让初始化顺序变成隐患（阶段三讲 `init` 时会再展开）。

命名上也有 Go 自己的习惯：短作用域用短名字（`i`、`n`、`err`），作用域越大名字越要完整；用驼峰而不是下划线；常见缩写保持一致的大写，如 `HTTPServer`、`userID`。首字母大小写同时承担可见性，所以命名不只是好看，它直接决定这个标识符能不能被别的包用。

<Callout type="tip" title="一个排查技巧" text="遇到变量赋值后好像没生效，先沿着花括号往外看一遍：是不是在某层里用 := 又声明了同名变量。这类问题 go vet 的 shadow 相关检查能帮一部分忙，但根本办法还是让作用域尽量小、名字尽量不重复。" />

## 小结与下一讲

- `var` 与 `:=` 各有位置限制；零值保证声明即可用，避免未初始化崩溃。
- `const` 加 `iota` 让一组相关常量自动编号，表达式可沿用，魔法数字因此变少。
- 作用域由花括号划分，内层同名声明会遮蔽外层；命名大小写决定跨包可见性。
