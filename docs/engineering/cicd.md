# 第 60 讲 · CI/CD、Makefile、代码生成与发布

> 前面十讲讨论的都是「代码本身好不好」，这一讲讨论「好代码怎么稳定地送到线上」。手工发版的典型剧本是：某个人在自己机器上 `go build`，scp 到服务器，出问题时说不清这是哪个版本、也找不回上一版。CI/CD 的价值不是多一个 yaml 文件，而是把「检查、测试、构建、发布」固化成**任何人、任何时间执行结果都一样**的一条线。

## 这一讲你会得到什么
<CheckList id="goal-60" title="本讲目标" :items='["用 Makefile 把常用命令收敛成一致入口","写出 GitHub Actions 工作流，把检查与测试设为合并门禁","用 go generate 与 -ldflags 管理生成物和版本，做到制品可回滚"]' />

## 1. 先建立直觉

把发布想成一条装配流水线：代码一进线，先过格式与静态检查，再跑测试，接着生成代码并确认生成物没有漂移，然后构建出带版本号的制品，最后打 tag 上线。每一站都是一道门禁，任何一站红灯，后面的站点根本不会启动。而「可回滚」的意思是：流水线的出口永远保留着上一个已验证的制品，出问题时能原样退回去。

<ConceptDiagram type="pipeline" title="CI 流水线：把检查到发布固化成一条线" labels="代码提交::触发工作流|静态检查::vet 与 lint|测试与构建::test 加 build|制品发布::打 tag 上传产物" caption="CI 把检查、测试、构建、发布固化成一条可重复、可回滚的线" />

这里最重要的工程判断是：**本地能跑不算数，CI 能重复跑才算数**。所以 Makefile 与工作流里的命令必须完全一致，不许出现「本地用一条命令、CI 用另一条」。

## 2. 语法与规则

第一块代码是一个极简的代码生成器，演示 `go generate` 会把什么样的产物写进仓库。

```go
// 一个简单的代码生成器：由 go generate 触发，输出可编译的源码
package main

import (
	"fmt"
	"os"
	"text/template"
)

// 生成目标：明确的 DO NOT EDIT 头，提醒人别手改
const tpl = `// Code generated by gen_version.go; DO NOT EDIT.
package version

const Version = "{{.}}"
`

func main() {
	t := template.Must(template.New("v").Parse(tpl))
	f, err := os.Create("version_gen.go")
	if err != nil {
		fmt.Println("创建文件失败:", err)
		return
	}
	defer f.Close()
	if err := t.Execute(f, "v1.4.0"); err != nil {
		fmt.Println("生成失败:", err)
		return
	}
	fmt.Println("已生成 version_gen.go")
}
```

<OutputBox title="运行结果" output="已生成 version_gen.go" note="生成物必须提交进仓库，CI 里用 git diff --exit-code 检查它有没有漂移。" />

第二块讲版本：把版本号与提交号留给构建期注入，源码里只放兜底值。

```go
// 版本信息由构建期 -ldflags -X 注入，不写死在源码里
package main

import "fmt"

// Version 与 Commit 由 go build -ldflags 覆盖
var Version = "dev"
var Commit = "none"

func main() {
	fmt.Println("版本:", Version)
	fmt.Println("提交:", Commit)
}
```

```text
版本: dev
提交: none
```

```bash
go build -trimpath -ldflags "-X main.Version=v1.4.0 -X main.Commit=$(git rev-parse --short HEAD)" -o bin/app ./cmd/api
```

第三块为制品算摘要：发布时把校验和随制品一起存档，回滚与验签才有依据。

```go
// 发布制品校验：为二进制生成 SHA-256 摘要
package main

import (
	"crypto/sha256"
	"fmt"
	"io"
	"os"
)

func checksum(path string) (string, error) {
	f, err := os.Open(path)
	if err != nil {
		return "", err
	}
	defer f.Close()
	h := sha256.New()
	if _, err := io.Copy(h, f); err != nil {
		return "", err
	}
	return fmt.Sprintf("%x", h.Sum(nil)), nil
}

func main() {
	// 演示：对当前可执行文件自身求摘要
	self, err := os.Executable()
	if err != nil {
		fmt.Println("定位可执行文件失败:", err)
		return
	}
	sum, err := checksum(self)
	if err != nil {
		fmt.Println("计算摘要失败:", err)
		return
	}
	fmt.Println("摘要长度:", len(sum))
}
```

```text
摘要长度: 64
```

## 3. 深入一步

流水线的每一站都要有明确的失败语义：

| 环节 | 工具 / 命令 | 失败时 |
| --- | --- | --- |
| 格式与静态检查 | gofmt / go vet / golangci-lint | 直接阻断合并 |
| 测试 | go test -race -cover ./... | 阻断，保留失败日志 |
| 生成物一致性 | go generate ./... 加 git diff --exit-code | 阻断，说明生成物未提交 |
| 构建 | go build -trimpath -ldflags | 阻断，不产出半成品 |
| 发布与回滚 | tag、changelog、保留上一版制品 | 回滚到上一个已验证制品 |

流水线的速度也要治理：把格式检查、单元测试这类快关卡放前面，构建与集成测试放后面，红灯来得越早越省时间。生成物一致性检查放在构建之前，避免花了几分钟编译才发现生成文件没提交。门禁的价值一半在拦截，一半在反馈快慢。

<Term word="制品" text="构建产出的可部署单元（二进制或镜像），必须带唯一版本与校验和，才能被追溯和回滚。" />

<Callout type="warn" title="易错点：生成物与版本漂移" text="生成代码只在本地跑、生成物不入库，CI 会构建出和你机器上不一样的二进制；版本号写死在源码里，则每个 tag 都要改代码。两者都会让「这版到底是哪个版本」变成悬案。" />

## 4. 工程实践

先看 Makefile，它把本地与 CI 的命令统一成一个入口：

```makefile
GO ?= go
VERSION ?= $(shell git describe --tags --always --dirty)
LDFLAGS := -s -w -X main.Version=$(VERSION)

.PHONY: all fmt lint generate test bench build clean

all: lint test build

fmt:
	$(GO) fmt ./...

lint:
	test -z "$$(gofmt -l .)"
	$(GO) vet ./...

generate:
	$(GO) generate ./...
	git diff --exit-code

test:
	$(GO) test -race -cover ./...

bench:
	$(GO) test -bench=. -benchmem -count=6 ./...

build:
	$(GO) build -trimpath -ldflags "$(LDFLAGS)" -o bin/app ./cmd/api

clean:
	rm -rf bin
```

再把它接进 GitHub Actions，让同一组命令在干净的机器上重跑一遍：

```yaml
# .github/workflows/ci.yml
name: ci
on:
  push:
    branches: [main]
  pull_request:
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-go@v5
        with:
          go-version: '1.22'
          cache: true
      - name: 格式与静态检查
        run: |
          test -z "$(gofmt -l .)"
          go vet ./...
      - name: 生成代码一致性
        run: |
          go generate ./...
          git diff --exit-code
      - name: 测试
        run: go test -race -cover ./...
      - name: 构建
        run: go build -trimpath -ldflags "-s -w -X main.Version=${{ github.sha }}" -o bin/app ./cmd/api
```

`git diff --exit-code` 是容易被漏掉的一招：它把「生成物有没有和源码一起提交」变成一道硬门禁，避免 CI 悄悄生成出与仓库不同的文件。`-trimpath` 去掉本机路径，让构建更可复现；`-s -w` 去掉调试符号缩小制品。版本与 changelog 由 tag 驱动，每次发布保留上一版制品与校验和，回滚就是把它重新部署，而不是紧急改代码重新构建。

<Compare title="手工发版与流水线发版" :panels='[{"label":"写法 A · 手工发版","code":"// 反例：本地构建后手动上传\nscp app prod:/srv/app\n// 没有 tag、没有旧制品、无法回滚","note":"说不清线上是哪一版，出事只能靠人肉回忆"},{"label":"写法 B · 流水线发版","code":"// 正例：CI 全链路\ngit tag v1.4.0\nmake build\n// 制品带版本号，保留上一版可回滚","note":"每版可追溯、可校验、可原样退回"}]' />

还有两个反模式值得点名：CI 里跑的命令和 Makefile 不一致，导致「本地绿、线上红」；以及只保留最新一个制品，回滚时才发现上一版早已被覆盖。发布不是构建的终点，可追溯与可回退才是。

<Callout type="tip" title="一条可执行的检查" text="在仓库里放一条 make ci 目标，内容就是工作流里那几行；要求所有人在提 PR 前本地先跑一遍，把 CI 变成可自检的约定。" />

## 小结与下一讲

- Makefile 与工作流共用同一组命令，检查、测试、构建、发布逐层设门禁。
- `go generate` 的产物入库并用 `git diff --exit-code` 防漂移；版本号由构建期注入。
- 制品带版本与校验和、保留上一版，回滚才是可执行动作。
- 至此阶段五结束：代码已经是可维护、可测试、可诊断、可发布的工程。
