# 第 007 讲 · 数值、布尔、字符与类型转换

> 数字大概是看起来最不需要学的东西，可生产事故里偏偏常见：金额算差一分、计数加到一半突然变负、把整数转成文本得到个莫名其妙的字母。Go 把数值类型分得很细，而且坚决不做隐式转换，正是为了让这些代价在代码里看得见。这一讲把整型宽度、浮点精度、byte 与 rune、以及显式转换一次讲清，之后遇到数字就不会凭直觉猜了。

## 1. 先建立直觉

把每个数值类型想成不同容量的盒子：`int8` 是只能装 −128 到 127 的小盒，`int64` 是大得多的盒子，而 `int` 是个"看机器而定"的盒子——在 32 位平台是 32 位，在 64 位平台是 64 位。往小盒里硬塞超出容量的东西，多出来的部分会被直接截掉，就像往量杯里倒过量的水，溢出的那截悄悄流走了，杯子不会提醒你。浮点则是另一种东西：它不是精确刻度，而是近似刻度，`0.1` 存进去其实已经有了一点点误差。

<ConceptDiagram type="value-pointer" title="值本身没变，变的是按哪种类型解释它" />

显式转换的本质是"把这份值按另一种类型重新装盒"，值本身没有变形，但盒子能表示的范围和精度变了。理解第 005 讲那句"值与装值的容器是两回事"，转换就不会显得神秘：你换的是容器，不是数据。

### 为什么 Go 把整型分得这么细，还坚决不做隐式转换

分两类不是为了难记，而是对应两种完全不同的需求。

`int8`、`int32`、`int64` 这类**固定宽度**类型，服务于"换台机器、换门语言，结果也必须一样"的场景：网络协议字段、文件格式、哈希、数据库列。若在这类地方用 `int`，32 位平台编出来的程序写出的文件，到 64 位平台上按 8 字节去读，数值就全错了——宽度成了隐藏在平台里的变量。

`int`、`uint` 这类**平台相关**类型，服务于只在本机使用的下标、长度、循环计数：宽度跟随目标平台的机器字长，通常运算最快，也不必关心它到底是 32 还是 64 位。

不做隐式转换的动机，是把"可能丢精度、改符号、溢出"的代价写在明面上。替代方案是自动类型提升，看起来省事，实则让编译器替你做了一个隐藏决策：`int + int64` 该往哪边提升、精度损失由谁承担、有符号与无符号混用时符号怎么处理，全都不出现在代码里。Go 选择把这次决策交还给人，于是 `int64(n)+8` 必须写出那次转换——写得见，才查得着。容量盒子类比里，"换盒子"这个动作本身被要求可见，正是这个意思。

### 三个能立刻跑的小实验

先读一眼"本机 int 到底几位"，这是一个编译期常量：

```go
package main

import (
	"fmt"
	"strconv"
)

func main() {
	fmt.Println("本机 int 位数：", strconv.IntSize)
}
```

<OutputBox title="实验一：int 宽度由平台决定" output="本机 int 位数： 64" />

`strconv.IntSize` 的值是 32 或 64，且是常量：它在编译期就定死，运行时不会变。把这段源码分别交叉编译到两个架构，能亲眼看到这条边界：

```bash
GOARCH=386 go build -o demo-386 size.go
GOARCH=amd64 go build -o demo-64 size.go
ls -l demo-386 demo-64
```

<OutputBox title="实验二：同一份源码，两种目标指令集（大小随版本而变）" output="-rwxr-xr-x  demo-386\n-rwxr-xr-x  demo-64" />

两个文件都能生成、体积却不同，原因是 `GOARCH` 改变了生成的机器指令，也改变了 `int` 的宽度。`ls` 是 Unix 命令，Windows 下换成 `dir`。这条实验正好解释了本讲工程实践里那句"写协议必须用 int32、uint64"：协议解析不能依赖一个会随编译目标改变的宽度。

再看 `go vet` 怎么抓"编译能过、结果却不是你以为的"那类写法：

```go
package main

import "fmt"

func main() {
	n := 65
	fmt.Println(string(n)) // 能编译，但 vet 会警告：把整数当码点
}
```

```bash
go vet ./...
```

<OutputBox title="实验三：整数转文本写错时的告警" output="./main.go:6:14: conversion from int to string yields a string of one rune, not a string of digits" />

逐项读：`./main.go:6:14` 是位置，后面那句说明这次转换得到的是"一个码点对应的字符"，而不是"一串数字"。正确写法是 `strconv.Itoa(n)`。把 `n` 换成 `n := 65` 再跑一次 `go vet`，输出为空即通过，一正一反把"显式转换"的必要性验证清楚。

最后把编译期常量溢出与运行时变量溢出的边界亲手撞一次：写 `var x int8 = 128` 后执行：

```bash
go build
```

<OutputBox title="实验四：常量溢出被编译器拦下" output="./main.go:5:14: constant 128 overflows int8" />

128 这个字面量在编译期就能算出超出 int8 上界，于是直接报错；而第一段代码里的 `small++` 是运行时变量，同样的超界只会安静回绕成 -128。两者对照，正是"什么时候该自己校验边界"这条结论的依据。

## 2. 语法与规则

先看整型宽度与溢出。`strconv.IntSize` 会告诉你本机 `int` 有多少位：

```go
package main

import (
	"fmt"
	"strconv"
)

func main() {
	var small int8 = 127 // int8 的上界
	small++              // 运行时回绕到 -128，编译器不会拦
	fmt.Println("int8 回绕：", small)
	fmt.Println("本机 int 位数：", strconv.IntSize)
}
```

<LineByLine code="var small int8 = 127\nsmall++\nfmt.Println(small)" :notes='["int8 只有 8 位，能表示的最大值是 127","自增 1 超出上界，运行时按二进制回绕成 -128","打印出来是负数，这就是静默溢出，不会抛异常也不会报错"]' />

<OutputBox title="运行结果（第二行随机器而变）" output="int8 回绕： -128\n本机 int 位数： 64" guess="true" />

这里要分清两种情况：**编译期常量**溢出（例如写 `var x int8 = 128`）会被编译器直接拦下；**运行时变量**的溢出如上所示会安静地回绕。后者才是真正的隐患，所以涉及计数、金额、序号时，要么选足够宽的类型，要么在运算前显式检查边界。

再看浮点。`0.1 + 0.2` 的结果值得一辈子记住，但要先避开一个 Go 特有的陷阱：

```go
package main

import (
	"fmt"
	"math"
)

func main() {
	x := 0.1              // 先把两个数存成 float64 变量
	y := 0.2
	a := x + y            // 运行时相加，误差才会显现
	fmt.Println("0.1 加 0.2：", a)
	fmt.Println("与 0.3 相等吗：", a == 0.3)
	fmt.Println("用误差判断：", math.Abs(a-0.3) < 1e-9)
	fmt.Println("保留两位：", math.Round(a*100)/100)
}
```

<OutputBox title="运行结果" output="0.1 加 0.2： 0.30000000000000004\n与 0.3 相等吗： false\n用误差判断： true\n保留两位： 0.3" guess="true" />

这里必须先存进变量再相加：如果直接写 `a := 0.1 + 0.2`，那是一个**常量表达式**，编译期会以任意精度算出精确的 0.3，赋给变量后与字面量 0.3 完全相等，反而看不到误差。只有参与运算的是运行时变量，二进制浮点的近似才会暴露出来——这是 Go 常量与变量行为不同的一处典型体现。

浮点用二进制近似表示十进制小数，因此直接用 `==` 判断相等几乎总是错的，正确做法是判断两者之差的绝对值是否小于一个可接受的误差。`math` 包提供 `Abs`、`Round`，以及 `MaxInt`、`MinInt` 这类边界常量，做范围检查时比手写魔法数字可靠。

第三段把转换与字符放在一起看：

```go
package main

import (
	"fmt"
	"strconv"
)

func main() {
	var n int = 42
	fmt.Println("转成 int64 后相加：", int64(n)+8) // 不同整型不能直接相加
	fmt.Println("正确的整数转文本：", strconv.Itoa(n))
	var r rune = 'A' // rune 是 int32 的别名，装一个字符的码点
	fmt.Printf("码点 %d 对应的字符是 %c\n", r, r)
	fmt.Println("把码点转成文本：", string(r))
}
```

<OutputBox title="运行结果" output="转成 int64 后相加： 50\n正确的整数转文本： 42\n码点 65 对应的字符是 A\n把码点转成文本： A" />

注意 `int64(n)+8`：Go 里 `int` 与 `int64` 是两种不同类型，不写这次转换就无法相加。也千万别把整数转文本写成 `string(65)`——那是把 65 当成一个<Term word="码点" text="Unicode 给每个字符分配的编号；rune 类型用来存放一个码点，本质是 int32。" />，得到的是字符 A，而不是文本 65，而且 `go vet` 会直接给出告警。

## 3. 深入一步

| 类型 | 宽度 | 典型用途 |
| --- | --- | --- |
| int8 / int16 / int32 / int64 | 8 / 16 / 32 / 64 位 | 明确需要固定宽度时用，如协议字段 |
| uint8 / uint16 / uint32 / uint64 | 对应无符号 | 位运算、长度、计数不为负的场景 |
| int / uint | 平台相关，32 或 64 位 | 日常下标、长度、循环计数 |
| uintptr | 刚好装得下指针 | 底层编程，业务代码基本不用 |
| byte | uint8 的别名 | 原始字节、二进制数据 |
| rune | int32 的别名 | 一个 Unicode 字符（第 008 讲细讲） |
| float32 / float64 | 32 / 64 位 | 科学计算；默认用 float64 |
| bool | true 或 false | 条件判断，不与数字互转 |

`byte` 与 `rune` 是最容易混的一对：`byte` 关心"一个字节"，`rune` 关心"一个字符"。英文字符两者恰好都是 1 字节，一遇到中文就分道扬镳——一个汉字在 UTF-8 里通常占 3 字节，却是 1 个 rune。这个差别是第 008 讲的主线，这里先记住别用 `byte` 去数中文个数。

<Callout type="warn" title="版本差异与三个坑" text="第一，Go 1.21 起内置了 min、max 函数（第 001 讲用过），但它们要求参数类型完全一致，混用 int 与 int64 仍需显式转换。第二，运行时整型溢出静默回绕，不会 panic。第三，string(整数) 是码点转字符、不是数字转文本，go vet 会告警；整数转文本请用 strconv.Itoa。第四，bool 与数字之间不能互转，Go 不认 1 等于 true 这套写法。" />

### 推导：为什么 0.1 加 0.2 不等于 0.3

原文给了现象，把二进制表示这一层补上，结论才不是死记的：

| 环节 | 发生了什么 |
| --- | --- |
| 十进制转二进制 | 0.1 在二进制里是无限循环小数，就像十进制里的 1/3 写成 0.333... 永远写不完 |
| 存进 float64 | 只有 53 位有效位，必须截断，存进去的已经是"略大一点点的 0.1" |
| 两个数相加 | 两份近似值各自带误差，误差累积到结果里 |
| 与 0.3 比较 | 得到 0.30000000000000004，严格相等判断自然是 false |

由此能推出三条工程结论，而不是背三条规矩：判等要用误差范围；金额要用整数分表示；需要任意精度时 `math/big` 才是答案，浮点不是。

还能再推一层，解释本讲那个看似奇怪的要求"必须先存进变量再相加"：常量表达式在编译期以任意精度计算，不受 float64 截断影响，所以直接写 `0.1 + 0.2` 作为常量恰好等于精确的 0.3，赋给变量后与字面量 0.3 完全相等。只有参与运算的是运行时变量，二进制浮点的近似才会暴露。这条"常量与变量行为不同"的边界，是本讲最容易被忽略的一处推导。

### 零基础最容易带进来的四个误解

| 错误理解 | 为什么站不住 | 正确理解 |
| --- | --- | --- |
| 浮点误差是 Go 的 bug，换门语言就没了 | 这是 IEEE 754 二进制浮点的普遍性质，十进制小数大多无法精确表示 | Python、Java、C 用二进制浮点都一样，判等一律用误差 |
| 金额乘 100 存成整数就万事大吉 | 若金额本来就是浮点数，乘法本身已经带进了误差 | 从输入就按整数分解析，或按小数点切分后再拼成整数 |
| int 与 int64 只是名字不同，混用没关系 | 它们是两种不同的类型，且 int 宽度随平台变化 | 必须显式转换；固定宽度场景用 int32、int64 |
| 浮点转整数会四舍五入 | 转换规则是直接丢掉小数部分 | `int(3.9)` 得到 3，要四舍五入得先 `math.Round` |

后两条配一段可编译代码一次验证：

```go
package main

import "fmt"

func main() {
	var u uint8 = 0
	f := 3.9
	fmt.Println("uint8 下溢：", u-1)
	fmt.Println("float 转 int 截断：", int(f))
	cents := 1999
	fmt.Println("金额：", cents/100, "元", cents%100, "分")
}
```

<OutputBox title="回绕、截断与整数分" output="uint8 下溢： 255\nfloat 转 int 截断： 3\n金额： 19 元 99 分" />

逐项读：`uint8` 减到 0 以下会回绕到 255，不会报错也不会变成 -1；`int(f)` 直接截掉小数，得到 3 而不是 4；金额全程用整数分，除法与取余都是精确运算。注意 `int(3.9)` 这种**字面量**写法会因常量截断而编译失败，所以代码里先存进变量 `f` 再转换。

### 版本与平台边界

| 边界 | 说明 | 归属 |
| --- | --- | --- |
| Go 1.21 | 内置 `min`、`max`，但要求参数类型完全一致，混用 int 与 int64 仍需显式转换 | 本讲、[第 001 讲](/guide/opening) |
| GOARCH | 386 上 int 为 32 位，amd64、arm64 上为 64 位；交叉编译出的产物因此不同 | 本讲实验二、[第 090 讲](/distributed/docker) |
| IEEE 754 | float32、float64 的精度与编码跨平台一致，浮点误差不随操作系统变化 | 与 int 宽度形成对照 |
| 操作系统 | 数值行为只与 GOARCH 有关，与 Windows、macOS、Linux 无关 | 平台差异集中在宽度与文件路径 |
| `go vet` | 整数转字符串的 stringintconv 检查从 Go 1.15 起提供，更旧的工具链不会报 | 本讲实验三 |
| `strconv.IntSize` | 编译期常量，可用于写平台兼容的分支判断 | 本讲实验一 |

## 4. 工程实践

金额是最典型的例子：绝不要用浮点存钱，正确做法是用整数表示最小单位（分），展示时再除以 100。这样既避开精度误差，也让加减法完全精确。同理，任何"差一点就相等"的判断都要换成误差比较，而不是 `==`。

边界上要主动设防：从外部读入的数字在参与运算前先校验范围，别等溢出回绕后再排查；循环计数、数组长度用平台相关的 `int` 就好，而写网络协议、文件格式时必须用 `int32`、`uint64` 这类固定宽度类型，否则换台机器解析结果就变了。`strconv.IntSize` 可以用来在运行时判断当前平台的 `int` 宽度，写兼容逻辑时比硬编码 64 稳妥。

`strconv` 包是文本与数值之间的正规通道：`Itoa`、`Atoi`、`FormatFloat`、`ParseFloat` 各司其职，其中 `Atoi` 这类解析函数会返回两个值，第二个是错误，第 020 讲会系统讲错误处理，现在只要记住"解析可能失败，不能假定一定成功"。真正需要任意精度整数或 decimal 时，标准库的 `math/big` 才是边界之外的答案，浮点不是。

## 小结与下一讲

- 整型有固定宽度与平台相关两类，`int` 的位数随机器变；运行时溢出静默回绕是必须设防的隐患。
- 浮点是近似表示，判等要用误差、金额要用整数分；`math` 提供取整与边界常量。
- `byte` 管字节、`rune` 管字符；类型之间一律显式转换，文本与数值之间走 `strconv`。
